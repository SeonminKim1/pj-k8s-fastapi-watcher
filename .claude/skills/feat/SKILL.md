# /feat

짧은 설명만 받아 PRD 초안부터 구현까지 `sdd-process.md`의 단계대로 진행한다. 시작 전에 `CLAUDE.md`, `sdd-process.md`(문서 템플릿·문서 관리 규칙), `docs/fastapi-sdd-template.md`(코드 규칙)를 읽는다.

## 사용법
```
/feat 유저가 주문을 생성한다. 1인당 하루 10건 제한.   # 새 기능
/feat api-order-create                                # 멈춘 단계부터 이어서
/feat api-order-create 쿠폰 필드 추가                  # 기존 기능 수정
```
끝에 "끝까지"를 붙이면 단계 사이의 확인만 생략하고 IMPLEMENT까지 진행한다. Grill 질문, TASK 검증, 진행 보고는 "끝까지"에서도 생략하지 않는다.

## 1. 모드 판별
- 인자의 첫 단어로 된 `docs/<첫 단어>/` 폴더가 있으면 **기존 기능**이다. 뒤에 설명이 없으면 "이어서", 있으면 "수정"으로 본다.
- 폴더가 없으면 **새 기능**이다.
- 인자가 없으면 무엇을 할지 묻는다.

## 2. 새 기능: PRD 초안 만들기
사용자가 PRD를 길게 쓰지 않아도 되게 하는 것이 목적이다.
1. 설명에서 `<feature-name>`을 추론한다(kebab-case, HTTP API는 `api-`, 백그라운드는 `component-` 접두사).
2. 설명, `CLAUDE.md` 요구사항, 기존 `docs/*/prd.md`를 참고해 `sdd-process.md`의 PRD 템플릿 항목을 Claude가 채운다.
   - 설명에서 바로 읽히는 내용은 그대로 쓴다.
   - `sdd-process.md`의 "Grill 규칙"과 PRD Grill 체크리스트로 점검하고, Claude가 정할 수 없는 것만 질문한다(PRD 한도 3개, AskUserQuestion으로 선택지 제시).
   - 질문 없이 추정으로 채운 항목에는 `(추정)`을 붙인다.
   - 이 기능에만 해당하지 않는 규칙(인증 방식, 공통 쿼터·정책 등)은 사용자에게 확인한 뒤 `CLAUDE.md`의 "프로젝트 상세 설명 (요구사항)"으로 옮기고, PRD에는 참조만 남긴다. 요구사항 섹션이 비어 있으면(첫 PRD) 특히 꼼꼼히 확인한다.
3. `docs/<feature-name>/prd.md`로 저장하고, feature-name과 PRD 요약을 보여주고 확인받는다. 수정 요청은 반영한다.
4. 확인되면 "3. 단계 진행"으로 넘어간다.

## 3. 단계 진행
- 폴더의 문서로 현재 단계를 판단한다.
  - `prd.md`만 있음 → SPEC
  - `spec.md`까지 있음 → PLAN
  - `plan.md`까지 있음 → TASK
  - `task.md`에 미완료 항목 있음 → IMPLEMENT
  - 모두 완료 → 완료 상태를 보고하고 끝낸다.
- 각 단계는 다음 순서로 진행한다.
  1. 그 단계의 Grill 체크리스트(`sdd-process.md`)를 스스로 점검한다.
  2. 정할 수 없는 것만 우선순위대로 질문한다(단계별 한도는 "Grill 규칙" 표). 한도를 넘은 항목은 가정과 함께 문서 끝 `## 확인 필요`에 남긴다.
  3. 템플릿대로 문서를 쓰고, 보여주고 확인받은 뒤 다음 단계로 간다. "끝까지"면 이 확인만 생략한다.
- **SPEC**: PRD에 없는 구현 디테일(Method/Path, 필드 타입, 상태 코드, 실행 방식 등)은 추측하지 않고 질문한다. 기존 `docs/*/spec.md`의 패턴(에러 코드, 응답 형태)을 맞춘다.
- **TASK**: 작업마다 선행 작업을 적고 실행 흐름(순차/병렬 단계)을 만든다. 실행 흐름을 보여주고 작업 계획 검증 질문 1~2개를 한 뒤, 사용자가 확인해야 IMPLEMENT로 넘어간다.
  - `CLAUDE.md`에 GitHub Project가 설정돼 있으면, 사용자가 확인한 뒤 `sdd-process.md`의 "GitHub Project 연동"대로 작업마다 이슈를 만들어 Project에 추가하고 `task.md`에 이슈 번호를 적는다. 만든 이슈 목록(번호, 제목)을 보고한다.
- **IMPLEMENT**:
  - `task.md`의 실행 흐름 단계 순서대로 구현한다. 병렬 단계의 작업은 한 번에 묶어 진행한다.
  - 이슈 번호가 붙은 작업은 시작할 때 Project Status를 `In Progress`로, 완료하면 `Done`으로 바꾸고 이슈를 닫는다. `gh` 실패는 보고만 하고 구현은 계속한다.
  - 단계 시작(▶), 작업 완료(✔), 단계 완료(■)마다 `sdd-process.md`의 "진행 보고" 형식으로 짧게 보고하고, `implement.md`의 `## 진행 기록`에도 남긴다.
  - spec·plan이 다루지 않는 상황을 만나면 추측하지 않는다. `⏸`로 보고하고 질문한 뒤, 해당 문서를 먼저 고치고 이어간다(되돌아가기).
  - 끝나면 완료 체크리스트(`ruff`, `pytest` 등)를 수행하고, README의 API 표를 갱신하고, `/code-review`를 권한다.

## 4. 기존 기능 수정
1. 변경 종류를 분류하고 사용자에게 알린다(`sdd-process.md`의 "작은 변경은 단계를 줄인다").
   - **버그·문구 수정** → 바로 구현, `implement.md`에 변경 섹션 추가
   - **동작 변경** → `spec.md` 수정 → `plan.md`·`task.md`에 변경 섹션 추가 → 구현
   - **규칙 변경** → `prd.md` 수정부터 시작
2. 문서는 `sdd-process.md`의 "문서 관리 규칙"대로 덮어쓰거나 추가한다. `task.md`에 변경 섹션으로 새 작업이 생기면 그 작업만 이슈로 만든다(GitHub Project 설정 시).
3. 서비스 전체 방향에 관한 변경이면 기능 문서보다 `CLAUDE.md` 요구사항 논의를 먼저 제안한다.
