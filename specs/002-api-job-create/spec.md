# 기능 명세: job 생성 API

- **브랜치**: `002-api-job-create`
- **작성일**: 2026-10-28
- **상태**: 확정
- **입력**: "유저가 템플릿 입력으로 job을 생성하는 API"

## 개요 (Overview)
- **배경/목적**: user-job 도메인(`specs/001-domain-user-job/`)은 service까지만 있고 외부에서 job을 만들 방법이 없다. 유저가 HTTP로 job을 등록할 수 있어야 operator가 이를 원하는 상태(desired)로 보고 클러스터에 반영할 수 있다. 유저가 매니페스트를 직접 쓰면 위험한 설정(privileged, hostPath, LoadBalancer, 리소스 제한 없음 등)을 막기 어려우므로, 템플릿 방식으로 입력 범위를 한정한다.
- **대상 사용자**: 게이트웨이를 거쳐 들어오는 서비스 유저(`X-User-Id`로 식별)
- **완료 기준**: 유저가 `X-User-Id`와 함께 `web` 타입 job을 요청하면, 서버가 생성한 Deployment·Service 매니페스트를 가진 `pending` 상태의 job이 MongoDB에 저장되고 응답으로 돌아온다. 잘못된 입력, 허용되지 않는 필드, 이름 중복, 개수 초과는 400으로 거절된다.
- **범위 제외**:
  - `web` 외 타입(batch, worker 등) → 필요할 때 타입 추가
  - 유저가 매니페스트를 직접 보내는 입력(JSON 원본, YAML)
  - job 조회·삭제 API → `003-api-job-list`, 이후 `api-job-get`·`api-job-delete`
  - 클러스터 리소스·네임스페이스 생성 → 이후 `component-job-operator`
  - 같은 요청을 여러 번 보낼 때의 멱등성 키(이름 중복 규칙으로 두 번째 요청은 400이 된다)
- **관련 요구사항**: `CLAUDE.md`의 "유저 식별", "유저별 네임스페이스", "유저별 job 개수 제한", "job 입력은 템플릿 방식", "에러 상태 코드", "operator 패턴"
  - `specs/001-domain-user-job/`: 이 기능에서 도메인의 `create_job`이 템플릿을 입력받고, job 문서에 유저 입력(`template`)과 한도 슬롯(`quota_slot`)을 저장하게 한다.

## 유저 시나리오와 테스트 (User Scenarios & Testing) *(필수)*

### 유저 스토리 1 - 템플릿으로 web job 등록 (우선순위: P1)
유저가 job 이름과 `web` 타입의 허용 필드(이미지, 포트, 레플리카, 환경 변수, 크기)만 보내면, 서버가 고정 값으로 매니페스트를 만들어 `pending` job으로 저장하고 돌려준다.

- **이 우선순위인 이유**: job을 만들 수 있어야 operator와 다른 API가 의미가 있다.
- **독립 테스트**: `POST /jobs`만으로 저장된 job과 서버가 만든 리소스 요약을 응답에서 확인할 수 있다.
- **인수 시나리오**:
  1. **Given** `alice`의 job이 없음, **When** 이름 `my-web`, 이미지 `nginx:1.27`, 포트 80으로 요청, **Then** 201, `status: pending`, `namespace: user-alice`, 리소스 `Deployment my-web`·`Service my-web`, 기본값(`replicas: 1`, `env: {}`, `size: small`)이 채워진 `template`.
  2. **Given** 유저 네임스페이스가 클러스터에 없음, **When** 생성 요청, **Then** 201(클러스터에는 쓰지 않는다).

### 유저 스토리 2 - 잘못된 요청 거절 (우선순위: P1)
유저가 형식이 틀리거나 고정 값을 바꾸려는 요청을 보내면 어느 필드가 왜 틀렸는지 400으로 알린다.

- **이 우선순위인 이유**: 템플릿 방식의 핵심은 입력 범위를 한정하는 것이다. 조용히 무시하면 유저가 고정 값이 바뀐 줄 안다.
- **독립 테스트**: 필드별 잘못된 요청마다 400과 해당 `code`를 확인한다.
- **인수 시나리오**:
  1. **Given** 정상 요청에서, **When** 이미지 `nginx:latest`, **Then** 400 `invalid_image`.
  2. **When** `template`에 정의되지 않은 필드(`hostNetwork`), **Then** 400 `invalid_parameter`.
  3. **When** 헤더 없음 + 다른 필드도 틀림, **Then** 400 `invalid_user_id`(우선순위가 가장 높은 하나만).

### 유저 스토리 3 - 한도와 이름 중복 (우선순위: P2)
유저당 삭제되지 않은 job은 10개까지이고, 같은 이름은 하나만 있다.

- **이 우선순위인 이유**: 서비스 전체 규칙(`CLAUDE.md`)을 API 경계에서 지킨다.
- **독립 테스트**: 10개 생성 후 11번째, 같은 이름 두 번, 동시 요청으로 확인한다.
- **인수 시나리오**:
  1. **Given** job 10개, **When** 11번째 요청, **Then** 400 `job_quota_exceeded`.
  2. **Given** `my-web`이 있음, **When** 같은 이름으로 요청, **Then** 400 `job_name_duplicated`.
  3. **Given** job 10개, **When** 중복 이름으로 요청, **Then** 400 `job_quota_exceeded`(한도가 먼저).
  4. **Given** 새 유저, **When** 동시에 15개 요청, **Then** 201 10개, 400 5개.

### 엣지 케이스 (Edge Cases)
- 헤더가 없거나 형식이 틀릴 때? body가 JSON이 아닐 때 헤더도 없으면?
- 필드가 여러 개 틀렸을 때 무엇을 알리나?
- `template`이나 body에 정의되지 않은 필드가 있을 때?
- 이미지에 태그가 없거나 `latest`일 때? digest가 함께 있으면?
- 포트·레플리카·env 개수·env 값 길이가 경계값(0, 최대, 최대+1)일 때?
- 한도가 찬 상태에서 이름도 중복일 때? 동시 요청으로 슬롯·이름이 함께 걸릴 때?
- 삭제된 job과 같은 이름으로 만들 때?
- MongoDB 오류일 때?

## 요구사항 (Requirements) *(필수)*

### 기능 요구사항 (Functional Requirements)
- **FR-001**: 유저는 job 이름과 템플릿 입력(타입과 그 타입이 허용하는 필드)만으로 job을 등록할 수 있어야 한다. 지금 지원하는 타입은 `web` 하나다.
- **FR-002**: 시스템은 템플릿으로 매니페스트(`web`: Deployment 1개 + Service 1개)를 생성하고, 네임스페이스·리소스 이름·라벨·리소스 크기·보안 설정·Service 타입은 서버 고정 값으로 정해야 한다.
- **FR-003**: 시스템은 job을 `pending` 상태로 저장하고 바로 응답하며, 클러스터에는 쓰지 않아야 한다.
- **FR-004**: 응답은 job ID, 이름, 네임스페이스, 상태, 기본값이 채워진 템플릿, 리소스 요약, 시각만 담고, 소유자·삭제 정보·매니페스트 본문은 담지 않아야 한다.
- **FR-005**: 정의되지 않은 필드가 있으면 거절해야 한다(고정 값을 바꾸려는 시도를 무시하지 않는다).
- **FR-006**: 잘못된 요청은 400으로 응답하고, 필드별 에러 하나(정해진 우선순위의 첫 번째)로 무엇이 왜 틀렸는지 알려야 한다.
- **FR-007**: 유저당 삭제되지 않은 job 10개를 넘으면 거절해야 한다(동시 요청 포함).
- **FR-008**: 삭제되지 않은 자기 job과 같은 이름이면 거절해야 한다(동시 요청 포함). 한도 초과가 이름 중복보다 먼저다.
- **FR-009**: API 문서에는 실제로 돌려주는 응답(201, 400, 500)만 보이고, 요청·응답 예가 실제 값으로 보여야 한다.

### 핵심 엔티티 (Key Entities)
- **UserJob**: `specs/001-domain-user-job/`의 job. 유저 입력(템플릿)과 한도 슬롯을 가진다.
- **JobTemplate (`web`)**: 이미지, 포트, 레플리카 수, 환경 변수, 크기 프리셋.

## 성공 기준 (Success Criteria) *(필수)*
- **SC-001**: 유저가 템플릿 필드만으로 job을 등록하고 응답에서 서버가 만든 리소스를 확인할 수 있다.
- **SC-002**: 에러 표의 모든 행이 해당 `code`의 400으로 응답한다.
- **SC-003**: 동시 요청에서도 유저당 job이 10개를 넘지 않는다.
- **SC-004**: `/docs`·`/redoc`에 실제로 쓰지 않는 응답(422)이 없고, 요청·응답 예가 실제 값이다.

## 가정 (Assumptions)
- 이미지 레지스트리는 제한하지 않고 형식만 검사한다.
- env에 비밀값을 넣지 말라고 안내만 한다(평문 저장).
- 같은 요청 재전송은 이름 중복 400으로 충분하다(멱등성 키 없음).

## 확인 필요
- **이미지 레지스트리 제한**: 형식만 검사하고 어느 레지스트리든 허용한다. 사내 레지스트리만 허용해야 하면 서비스 전체 규칙으로 `CLAUDE.md`에 추가한다.
- **비밀값**: env에 비밀값을 넣지 말라고 안내만 한다. 비밀값 저장 방식은 비밀번호가 필요한 템플릿(`db` 등)을 추가할 때 함께 정한다.
