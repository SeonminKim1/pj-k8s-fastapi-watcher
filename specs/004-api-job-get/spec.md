# 기능 명세: job 단건 조회 API

- **브랜치**: `004-api-job-get`
- **작성일**: 2026-11-06
- **상태**: 초안
- **입력**: "유저가 job ID로 자기 job 하나의 상세(템플릿, 리소스 포함)를 조회한다."

## 개요 (Overview)
- **배경/목적**: 목록 조회(`specs/003-api-job-list/`)는 요약(ID, 이름, 상태, 생성 시각)만 돌려준다. 유저가 job을 만들 때 넣은 템플릿 값(이미지, 포트, 레플리카, 환경 변수, 크기)과 서버가 만든 리소스를 다시 확인할 방법이 없다. 생성 응답을 잃어버리면 내 job이 어떤 설정으로 돌고 있는지 알 수 없다.
- **대상 사용자**: 게이트웨이를 거쳐 들어오는 서비스 유저(`X-User-Id`로 식별)
- **완료 기준**: 유저가 자기 job의 ID로 요청하면 생성 응답과 같은 상세(이름, 네임스페이스, 상태, 기본값이 채워진 템플릿, 리소스 요약, 시각)가 돌아오고, 남의 job·없는 job·삭제된 job은 모두 "없음"으로 거절된다.
- **범위 제외**:
  - 매니페스트 본문 조회(서버 고정 값이라 유저에게 보여 주지 않는다)
  - 클러스터의 실시간 상태(Pod 상태, 이벤트, 로그)
  - 삭제된 job 조회(이력 보기)
  - 이름으로 조회(ID만)
  - job 수정·삭제 → 이후 `api-job-delete` 등
- **관련 요구사항**: `CLAUDE.md`의 "유저 식별", "에러 상태 코드"(남의 리소스는 없음과 같게), "operator 패턴"(상태는 operator가 마지막으로 기록한 값)
  - `specs/001-domain-user-job/`: 도메인의 단건 조회 규칙을 그대로 쓴다.
  - `specs/002-api-job-create/`: 상세의 모양은 생성 응답과 같다. 요청 검증 에러 처리도 같은 방식이다.

## 유저 시나리오와 테스트 (User Scenarios & Testing) *(필수)*

### 유저 스토리 1 - 내 job 상세 보기 (우선순위: P1)
유저가 목록이나 생성 응답에서 얻은 job ID로 그 job의 설정과 상태를 본다.

- **이 우선순위인 이유**: 이 기능의 전부다. 템플릿 값과 리소스를 다시 볼 수 있어야 한다.
- **독립 테스트**: job 하나를 만든 뒤 그 ID로 조회해 생성 응답과 같은 내용인지 확인한다.
- **인수 시나리오**:
  1. **Given** `alice`의 job `my-web`(기본값으로 생성), **When** `alice`가 그 ID로 조회, **Then** 이름, 네임스페이스 `user-alice`, 상태, 기본값이 채워진 템플릿, 리소스 요약(Deployment·Service)이 생성 응답과 같게 돌아온다.
  2. **Given** operator가 상태를 `running`으로 바꿈, **When** 조회, **Then** 상태는 `running`, 마지막 변경 시각이 바뀐 값이다.

### 유저 스토리 2 - 내 것이 아니면 없음 (우선순위: P1)
남의 job, 없는 job, 삭제된 job, 형식이 틀린 ID는 모두 같은 "없음"으로 거절된다.

- **이 우선순위인 이유**: 다른 유저 job의 존재가 드러나면 안 된다(`CLAUDE.md` "에러 상태 코드").
- **독립 테스트**: 네 경우를 각각 요청해 같은 응답인지 확인한다.
- **인수 시나리오**:
  1. **Given** `bob`의 job, **When** `alice`가 그 ID로 조회, **Then** "없음" 에러.
  2. **Given** `alice`가 job을 삭제함, **When** 그 ID로 조회, **Then** "없음" 에러.
  3. **When** ID 형식이 아닌 값(`abc`)으로 조회, **Then** "없음" 에러(형식 오류로 따로 알리지 않는다).
  4. **When** 유저 ID 헤더 없이 조회, **Then** 유저 ID 형식 에러(없음보다 먼저).

### 엣지 케이스 (Edge Cases)
- 유저 ID가 없거나 형식이 틀릴 때? 그때 job ID도 틀리면 무엇을 알리나?
- job ID 형식이 틀렸거나, 형식은 맞지만 없는 ID일 때?
- 남의 job ID일 때(존재 여부가 드러나면 안 됨)?
- 삭제된 job일 때? 삭제 후 같은 이름으로 새로 만든 job과 섞이지 않나?
- MongoDB 오류일 때?

## 요구사항 (Requirements) *(필수)*

### 기능 요구사항 (Functional Requirements)
- **FR-001**: 유저는 job ID로 삭제되지 않은 자기 job 하나의 상세를 볼 수 있어야 한다.
- **FR-002**: 상세는 생성 응답과 같은 항목(ID, 이름, 네임스페이스, 상태, 기본값이 채워진 템플릿, 리소스 요약, 생성·변경 시각)을 담고, 소유자·삭제 정보·매니페스트 본문은 담지 않아야 한다.
- **FR-003**: 남의 job, 없는 job, 삭제된 job, 형식이 틀린 job ID는 모두 같은 "없음"으로 응답해 서로 구분되지 않아야 한다.
- **FR-004**: 유저 ID가 없거나 형식이 틀리면 job 조회 전에 유저 ID 형식 에러로 거절해야 한다.
- **FR-005**: 상태는 operator가 마지막으로 기록한 값이며, 조회는 클러스터에 접근하지 않아야 한다.

### 핵심 엔티티 (Key Entities)
- **job 상세**: `specs/002-api-job-create/`의 생성 응답과 같은 항목.

## 성공 기준 (Success Criteria) *(필수)*
- **SC-001**: 유저가 job ID 하나로 그 job을 만들 때의 설정을 모두 다시 확인할 수 있다.
- **SC-002**: 남의 job·없는 job·삭제된 job·잘못된 ID에 대한 응답이 서로 같아 존재 여부를 알 수 없다.

## 가정 (Assumptions)
- 매니페스트 본문은 응답하지 않는다. 생성 응답과 같은 기준이고, 고정 값은 서버 문서(`specs/001-domain-user-job/data-model.md`)로 알 수 있다.
- 상세의 모양은 생성 응답과 같게 해 클라이언트가 같은 모델을 쓴다. 항목을 늘릴 필요가 생기면 두 응답에 함께 더한다.
- 형식이 틀린 job ID도 "없음"으로 본다(도메인의 단건 조회 규칙).
