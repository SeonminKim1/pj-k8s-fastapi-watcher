# 기능 명세: job 목록 조회 API

- **브랜치**: (이관 전 `feature/api-job-list`)
- **작성일**: 2026-10-29 (2026-11-06 `docs/api-job-list/`에서 이관, 옛 PRD·SPEC은 git 이력)
- **상태**: 확정 (구현 완료)
- **입력**: "유저가 자기 job 목록을 cursor 페이지네이션과 status 필터로 조회하는 API"

## 개요 (Overview)
- **배경/목적**: 유저는 job 생성 API(`specs/002-api-job-create/`)로 job을 등록할 수 있지만, 등록한 job과 그 진행 상황(`status`)을 다시 볼 방법이 없다. 생성 응답의 job ID를 잃어버리면 자기 job을 찾을 수 없고, operator가 바꾼 `status`(`pending` → `running`/`failed`)도 확인할 수 없다(`CLAUDE.md`의 "operator 패턴": 유저는 job `status`로 진행 상황을 본다).
- **대상 사용자**: 게이트웨이를 거쳐 들어오는 서비스 유저(`X-User-Id`로 식별)
- **완료 기준**: 유저가 `X-User-Id`와 함께 목록을 요청하면 삭제되지 않은 자기 job의 요약이 최신순으로 돌아오고, `next_cursor`로 다음 페이지를 이어 받을 수 있으며, `status`를 지정하면 그 상태의 job만 돌아온다. 다른 유저의 job과 삭제된 job은 나오지 않는다. 잘못된 헤더·쿼리 값은 400으로 거절된다.
- **범위 제외**:
  - job 단건 상세 조회(템플릿·리소스 포함) → 이후 `api-job-get`
  - job 삭제 → 이후 `api-job-delete`
  - 삭제된 job 조회(이력 보기)
  - 이름 검색, 생성 시각 범위 등 `status` 외 필터, 정렬 기준 변경
  - 클러스터의 실시간 상태 조회(Pod 상태 등)
  - 전체 개수(total count) 응답
- **관련 요구사항**: `CLAUDE.md`의 "유저 식별", "유저별 job 개수 제한", "에러 상태 코드", "operator 패턴"
  - `specs/002-api-job-create/`: 요청 검증 에러 처리(`to_error_enum()`)와 에러 응답 형태를 그대로 따른다.

## 유저 시나리오와 테스트 (User Scenarios & Testing) *(필수)*

### 유저 스토리 1 - 내 job 목록 보기 (우선순위: P1)
유저가 자기 job 요약(이름, 상태, 생성 시각)을 최신순으로 본다.

- **이 우선순위인 이유**: job ID를 잃어도 자기 job을 찾고 operator가 바꾼 상태를 확인할 수 있어야 한다.
- **독립 테스트**: job을 몇 개 만든 뒤 `GET /jobs`만으로 확인한다.
- **인수 시나리오**:
  1. **Given** `alice`의 job 5개와 `bob`의 job 1개, **When** `alice`로 조회, **Then** `alice`의 job 5개가 최신순, `next_cursor: null`.
  2. **Given** `alice`의 job 하나가 삭제됨, **When** 조회, **Then** 삭제된 job은 나오지 않는다.
  3. **Given** job이 없음, **When** 조회, **Then** `items: []`, `next_cursor: null`(404 아님).

### 유저 스토리 2 - 나눠 받기 (우선순위: P2)
유저가 한 페이지 개수를 정하고 `next_cursor`로 다음 페이지를 이어 받는다.

- **이 우선순위인 이유**: 지금은 한도(10개) 때문에 한 페이지로 끝나지만, 한도가 커져도 API 형태가 바뀌지 않게 처음부터 둔다.
- **독립 테스트**: 작은 `limit`으로 끝까지 넘겨 빠짐·겹침이 없는지 확인한다.
- **인수 시나리오**:
  1. **Given** job 5개, **When** `limit=2`로 끝까지, **Then** `[2개] [2개] [1개]`, 마지막만 `next_cursor: null`.
  2. **Given** 같은 시각에 만든 job이 페이지 경계에 걸림, **When** 넘김, **Then** 빠지거나 겹치지 않는다.
  3. **Given** cursor가 가리키던 job이 그사이 삭제됨, **When** 그 cursor로 요청, **Then** 그 위치 뒤가 정상으로 이어진다.

### 유저 스토리 3 - 상태로 거르기 (우선순위: P3)
유저가 `status` 하나를 지정해 그 상태의 job만 본다.

- **이 우선순위인 이유**: 실패한 job만, 실행 중인 job만 보는 것이 가장 흔한 확인이다.
- **독립 테스트**: 상태가 섞인 job으로 필터 결과를 확인한다.
- **인수 시나리오**:
  1. **Given** `running` 2개·`pending` 3개, **When** `status=running`, **Then** 2개만.
  2. **When** `status=running&status=failed`, **Then** 400 `invalid_job_status`(하나만 허용).

### 엣지 케이스 (Edge Cases)
- 헤더가 없거나 형식이 틀릴 때? 헤더 오류와 쿼리 오류가 함께 있을 때?
- `limit`이 0, 101, 정수가 아님, 빈 값일 때?
- 같은 쿼리를 여러 번 보낼 때? 정의되지 않은 쿼리가 있을 때?
- cursor가 빈 값, base64url이 아님, 조작됨, 범위를 벗어난 시각일 때?
- 다른 유저의 cursor를 보낼 때(남의 job이 드러나면 안 됨)?
- 페이지를 넘기는 사이 새 job이 생기거나 상태가 바뀔 때?
- MongoDB 오류일 때?

## 요구사항 (Requirements) *(필수)*

### 기능 요구사항 (Functional Requirements)
- **FR-001**: 유저는 삭제되지 않은 자기 job의 요약(ID, 이름, 상태, 생성 시각)을 볼 수 있어야 한다. 다른 유저의 job과 삭제된 job은 나오지 않는다.
- **FR-002**: 목록은 최신순이며, 같은 시각이면 ID 순으로 순서가 정해져야 한다.
- **FR-003**: 유저는 한 페이지 개수(기본 20, 1~100)를 정하고, 직전 응답의 불투명 cursor로 다음 페이지를 이어 받을 수 있어야 한다. 다음 페이지에 항목이 있을 때만 cursor를 준다.
- **FR-004**: cursor는 위치만 뜻해야 한다. 가리키던 job이 삭제·변경돼도 이어지고, 다른 유저의 cursor로 남의 job이 드러나지 않는다.
- **FR-005**: 유저는 상태 하나로 거를 수 있어야 한다. 여러 상태를 한 번에 거르지 않는다.
- **FR-006**: 같은 쿼리를 여러 번 보내거나 값이 비었거나 범위 밖이면 거절해야 한다. 정의되지 않은 쿼리는 무시한다.
- **FR-007**: 잘못된 요청은 400으로 응답하고 필드별 에러 하나(정해진 우선순위의 첫 번째)를 알려야 한다. 풀 수 없는 cursor도 400이다.
- **FR-008**: MongoDB만 읽고 클러스터는 조회하지 않는다. 상태는 operator가 마지막으로 기록한 값이다.

### 핵심 엔티티 (Key Entities)
- **JobSummary**: 목록 한 항목. job ID, 이름, 상태, 생성 시각.
- **페이지**: 이번 페이지 항목과 다음 페이지 cursor.
- **cursor 위치**: 정렬 순서상 위치(생성 시각, ID). 소유자 정보는 담지 않는다.

## 성공 기준 (Success Criteria) *(필수)*
- **SC-001**: 유저가 job ID 없이도 자기 job과 최신 상태를 찾을 수 있다.
- **SC-002**: 어떤 `limit`으로 끝까지 넘겨도 job이 빠지거나 겹치지 않는다.
- **SC-003**: 에러 표의 모든 행이 해당 `code`의 400으로 응답한다.

## 가정 (Assumptions)
- 삭제된 job은 목록에서 뺀다(`specs/001-domain-user-job/`의 `list_jobs` 정의).
- 유저당 job이 10개라 인덱스는 바꾸지 않는다(한도가 커지면 다시 본다).
